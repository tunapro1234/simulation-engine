# simengine.bench.tasks.m5

M5 demand forecasting as a bench task. The data is Walmart daily unit sales: 30,490 item x store series, 3,049 items,
10 stores in 3 US states, from 2011-01-29 to 2016-06-19, as released for the M5 Accuracy competition (Kaggle /
University of Nicosia, 2020). The task is to forecast the next 28 days for every series. It is scored with the
competition's WRMSSE over 12 aggregation levels and, as a second metric, bottom-level WMAPE. The task wraps
`simengine.methods.forecast`: its baselines are that module's forecasters, and a user method is any forecaster that
takes the same long panel.

## API

```python
from simengine import bench
from simengine.bench.tasks import m5            # registers "m5" (until the package __init__ imports it)
from simengine.methods import forecast as fc

task = m5.M5()                                   # or bench.get("m5", split="validation", n_series=3000)
data = task.load("/path/to/catalogue")           # or $SIMENGINE_DATA; TaskData(train, test, meta)
mine = lambda d: m5.align(d, fc.moving_mean(m5.future_panel(d), d.meta["origin"], 28, window=28, **m5.COLS))
frame = task.run(methods={"ma28": mine}, data=data, baselines="snaive")
task.score(frame, "ma28")                        # {'metric': 'wrmsse', 'value', 'lo', 'hi', 'n', 'higher_is_better'}
task.score_all(frame, B=1000)                    # every method x (wrmsse, wmape)
m5.wrmsse_by_level(frame, "ma28")                # levels 1-12 + average, comparable with the M5 paper's Table B
```

- **Data.** `data.train` and `data.test` are long panels in the `methods.forecast` layout (`m5.COLS`: `id_col="id"`,
  `time_col="d"`, `y_col="sales"`). `d` is the integer M5 day, with d_1 = 2011-01-29, and
  `id = item_id + "_" + store_id`. Every row also carries the series keys (`item_id`, `dept_id`, `cat_id`,
  `store_id`, `state_id`, all categorical) and covariates of its own day that are known in advance: `sell_price`
  (NaN before the item's first price), `wday` (M5 calendar, 1 = Saturday), `snap` (a SNAP day in the series' state)
  and `event` (any named event). `data.train` holds the last `history` days up to the origin. `data.test` holds the
  28 days after it, with `h` = 1..28 and `sales` as the truth.
- **Helpers.** `m5.future_panel(data)` returns train + test with `sales` set to NaN, which is the input a
  `methods.forecast` forecaster takes at `data.meta["origin"]`. `m5.align(data, fr)` maps a forecast frame
  `[id, d (or origin + h), pred]` onto the `data.test` rows. A method returns one number per test row.
- **Options.**
  - `split`: `"evaluation"` (the default; origin d_1941, test d_1942-1969, the competition's final private-leaderboard
    window), `"validation"` (origin d_1913, test d_1914-1941, the public-leaderboard window) or `"dev"` (origin d_1885,
    test d_1886-1913, which touches neither window).
  - `origin`: any last training day; it overrides `split`.
  - `history`: training days kept in `data.train` (default 730).
  - `n_series`: a random subsample of series drawn with `default_rng(seed)`.
  - `stores`: a `+`-joined store filter, applied before `n_series`.
  - `seed`: default 0.
  - `baselines`: a `+`-joined subset of the baselines below.
  - `lgb_origins`: default 28.
  - `lgb_jobs`: LightGBM threads, default 1.

  Unknown options raise an error.
- **Meta.** `meta` holds the origin, the split rule, the calendar, `levels` (one row per aggregate series: level, keys,
  bottom count, dollar sales, weight, scale), `series` (per bottom id, the weight and scale of its aggregate at each
  level) and the licence line.
- **EvalFrame.** One row per (series, day). Columns: `unit` (`id|d_n`), `group` (id), `item` (item_id), `time` (date),
  `d`, `h`, `truth`, `segment` (category), `seg_store`, `seg_state`, the five key columns, and `w_L1..w_L12` /
  `sc_L1..sc_L12`. The last two sets hold the weight and scale of the row's aggregate at each level, so the frame can
  be scored on its own.
- **Free functions.** `wrmsse(frame, method)`, `wrmsse_by_level`, `level_scores`, `rmsse_scale(A)`,
  `hierarchy(keys, Y_hist, dollars)`, `level_codes`, `ets_lite(panel, origin, horizon, ...)`, `read_sales`,
  `read_calendar`, `price_matrix`.

## Data layout and provenance

The task reads `<root>/m5-walmart/` (or the root itself, or an `m5/` subdirectory). It accepts either `m5.zip`, as
zipped by the Nixtla `m5-forecasts` GitHub mirror and read in place without extracting, or the extracted
`sales_train_evaluation.csv`, `sales_test_evaluation.csv` (needed only when the test window goes past d_1941),
`calendar.csv` and `sell_prices.csv`. The mirror carries no licence file, so the Kaggle competition's data terms
apply. Treat the data as internal research use only and do not redistribute it.

## Metrics

Both metrics follow Makridakis, Spiliotis & Assimakopoulos (2022), "M5 accuracy competition: Results, findings, and
conclusions", IJF 38(4), section 3.3. That definition was checked against the paper's text before implementing.

- **`wrmsse` (primary).** For each series, RMSSE = sqrt(mean_h (y - y_hat)^2 / scale).
  - The scale is the in-sample one-step naive MSE of the training history. It is counted only from the series' first
    non-zero sale up to the origin, and it uses every day in the file, not only `history`.
  - Bottom forecasts are summed to the 42,840 series of the 12 levels (bottom-up). The levels are total, state, store,
    category, department, state x category, state x department, store x category, store x department, item,
    item x state and item x store.
  - Weight = dollar sales (units x `sell_price`) over the last 28 training days, normalised within each level.
    WRMSSE = mean over levels of sum_s w_s RMSSE_s.
  - On the full data the computed weights match the official `weights_validation.csv` and `weights_evaluation.csv` for
    every level and every key. The largest absolute difference was 2.6e-10, and the dollar totals were identical
    (3,748,180.05 and 3,900,976.02). This check ran once with a local script against the release files and is not a
    unit test, because those files are data rows.
- **`wmape`.** sum |y - y_hat| / sum y over the bottom-level test rows (`forecast.wmape`).
- **CI.** 95% percentile bootstrap, `default_rng(42)`, B = 1000.
  - WMAPE resamples the bottom series.
  - WRMSSE resamples the aggregate series within each level, so w and RMSSE move together and a level's value is
    sum c w RMSSE / sum c w. Each level is resampled independently, and the scales are held fixed.
  - Levels 1-5 have 1 to 10 series, so they add little or no width. The interval therefore covers cross-sectional
    sampling at the lower levels only. It is not a full hierarchical or temporal bootstrap.
- **Subsamples.** With `n_series` or `stores`, the hierarchy, weights and scales are those of the subsample, so the
  numbers are not comparable with full-M5 numbers.

## Baselines

Every baseline forecasts the bottom level, and the metric aggregates bottom-up, which is how the M5 benchmarks
1-10, 12 and 15 work.

| name | method |
|---|---|
| `naive` | last value (`forecast.persistence_forecast`) |
| `snaive` | same weekday last week (`forecast.seasonal_naive`, season 7); the M5 sNaive benchmark |
| `ses` | simple exponential smoothing with one global alpha, chosen by `forecast.ses` (WMAPE over 6 earlier origins, grid 0.05-0.7). The M5 SES benchmark instead picks alpha in [0.1, 0.3] per series by in-sample MSE |
| `ets_lite` | the `ses` level x a day-of-week index (7 x weekday share of sales over the last 8 weeks, pooled per store x department). A cheap stand-in for the M5 ES_bu benchmark (per-series ETS); not an ETS model |
| `lightgbm` | `forecast.DirectForecaster`: one Tweedie (power 1.2) LightGBM per horizon, so 28 models with the forecast module's default parameters. Features: lags 1/2/3/7/14/28, rolling mean and non-zero count over 7/28/56/112 days, the same weekday last week, and for the target day the price, `wday`, SNAP and event, plus store/dept/cat/state codes. Trained on the last 28 daily origins |

`lightgbm` uses daily origins (`origin_step=1`) on purpose. With `origin_step=7`, `DirectForecaster` trains horizon h
on origins p - h - 7k. Their weekday differs from the forecast origin's whenever h is not a multiple of 7, so the
model learns a shifted weekly pattern. On the synthetic test fixture this raised WRMSSE from 0.49 to 1.50, and a
unit test now guards against it.

## Measured numbers

Each table below comes from one run on the local catalogue on 2026-10-23, with all 30,490 series, history 730,
`lgb_jobs=8` and B = 1000. The driver was `run_m5.py <split> naive+snaive+ses+ets_lite+lightgbm`, a 30-line script
kept outside the repository and run under `nice -n 19`. Run from the repository root with the data under
`$SIMENGINE_DATA`, it does the same as:

```python
import pandas as pd
from simengine import bench
from simengine.bench.tasks import m5
task = m5.M5(split="evaluation", lgb_jobs=8)                    # or split="validation"
frame = task.run()
print(bench.to_markdown(task.score_all(frame, B=1000).assign(status="ok", is_baseline=True), primary_only=False))
print(pd.concat([m5.wrmsse_by_level(frame, b).set_index("level")["wrmsse"].rename(b)
                 for b in m5.BASELINES], axis=1).T)
```

Cost per split: about 7 minutes wall clock and 5.3 GB peak RSS. Loading took 10 s, each rule baseline 7-9 s and
`lightgbm` 370-390 s. An earlier run on 2026-10-22 gave the same values to the third decimal.

Cells are `value [95% CI]`.

**Check against the literature.** Makridakis et al. 2022, Appendix B, Table B, reports Naive 1.752 and sNaive 0.847
on this window. Our `naive` and `snaive` match both overall values, and all 12 per-level values, to the third
decimal. That is an end-to-end check of the scales, weights, aggregation and test window. The same table reports
SES 0.969, ES_bu 0.671, ES_td 0.720 and ARIMA_bu 0.908. Our `ses` (0.957) and `ets_lite` (0.763) are different
methods, so they are not reproductions of those benchmarks. Per Table 3 of the paper, the winning entry (YJ_STU)
scored 0.520 and all of the top 50 scored at most about 0.58. Our untuned `lightgbm` (0.675) lands near ES_bu
(0.671, paper) and well behind the top 50. Its gain over `ets_lite` is concentrated at the aggregate levels 1-9.
At the item levels 10-12 the two are within 0.03.

The ranking of `ses` and `snaive` flips between the two metrics. WRMSSE rewards weekly shape at the aggregate levels,
and WMAPE rewards a flat level at the bottom.

## Limitations

- The WRMSSE CI is a within-level series bootstrap with fixed scales. It ignores the dependence between levels and
  over time, so read it as a lower bound on the uncertainty. With one 28-day window, the gap between the two
  competition windows above (for example, `ses` 0.957 vs 1.069) is a better guide to origin-to-origin variation.
- `ses` and `ets_lite` are simplified and do not reproduce the M5 SES and ES_bu benchmarks.
- `lightgbm` is untuned: the forecast module's default parameters, with no categorical handling for item ids, no
  price-relative features and no tuned Tweedie power. It is a reference point, not a competitive entry.
- Only bottom-up forecasts are scored. A method that forecasts the upper levels directly has to reconcile its
  forecasts to the bottom level first.
- The task does not cover the M5 Uncertainty track (quantiles, WSPL).
- No LLM method is included. Event names are in `meta["calendar"]` if you want to build an
  `forecast.llm_prior_feature`.
